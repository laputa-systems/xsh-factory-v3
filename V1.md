# Factory V3 V1 backlog

## 1. Meaning and status

`V1` means the first release after the cleanroom MVP described by
`docs/ARCHITECTURE.md` and `docs/CONTROL-PLANE.md`.
It does not mean Factory V1 and does not authorize importing Factory V1 or V2
code or state.

This file preserves deliberately deferred work so the MVP does not grow
placeholder types, tables, traits, protocol fields, feature flags, or half-built
frameworks. An item here is not approved for implementation merely because it
is documented. Promotion requires:

1. the MVP acceptance campaign has delivered its XSH commit;
2. evidence identifies a real throughput, quality, operability, or safety
   constraint;
3. the Grand Architect explicitly selects the item;
4. its contracts and acceptance evidence are added to a new implementation
   plan before code; and
5. the change preserves the generic-factory/XSH-application boundary.

## 2. Self-upgrade and self-reconfiguration

### 2.1 Why it is deferred

Self-upgrade is valuable but not necessary to prove the core factory: Product
discovers a defect, the Architect sponsors it, Engineering fixes it, Quality
reviews it, and the kernel delivers a provenance-bearing commit. Automated
kernel/schema replacement adds a second product—an upgrade manager—with its
own database cloning, migration, boot, health, rollback, and recovery state.

Implementing it before the product circuit is proven risks making upgrade
concerns dictate every ordinary domain type and transaction. The MVP therefore
uses explicit offline operator deployment for the Rust kernel/host, the pinned
agent-core source, and schema changes. It records the installed
`KernelBuildId` for provenance but cannot replace itself.

### 2.2 Intended authority model

When promoted, the Grand Architect may authorize changes to application code,
the Rust kernel, database schema, qualification logic, and activation mechanism
itself. There is no claim of an immutable warden above future generations.

The system can prove a predecessor-authorized chain, exact candidate bytes,
qualification results, activation time, and retained recovery material. It
cannot prove that a future generation will preserve today's safeguards after
that generation is authorized to change the safeguards themselves. That limit
must remain explicit.

Application-only declarative revision changes are already an MVP capability and
do not require this machinery. V1 self-upgrade concerns executable Rust,
schema, qualification, and activation changes.

### 2.3 Factory-change circuit

A self-change begins with a typed Architect request stating:

- objective and expected operational improvement;
- affected trusted boundary;
- exact acceptance tests;
- schema/migration impact;
- rollback boundary; and
- evidence that an application-policy change is insufficient.

The intended circuit is:

1. A fresh Engineering session works in an isolated V3 source worktree and
   submits a source tree plus any migration.
2. The incumbent kernel runs the complete provider-free V3 qualification set.
3. A fresh Quality session reviews the exact source/tree/migration and invokes
   the same qualification set again.
4. The Architect accepts or rejects the exact candidate generation.
5. The incumbent generation alone packages, clone-qualifies, and activates an
   accepted successor.

The candidate never writes incumbent state or certifies itself.

### 2.4 Candidate generation package

The immutable package should contain:

- predecessor generation identity;
- source commit/tree and portable patch artifact;
- Rust binaries with BLAKE3 and byte length;
- checked Rust source graphs, Cargo lock/toolchain identity, and the exact
  `pi-agent-core-rs` checkout identity;
- a populated, offline-verified Cargo dependency materialization;
- ordered SQL migration artifacts and expected resulting schema identity;
- application revision set;
- exact qualification command-set revision;
- Engineering, deterministic-test, and Quality receipts; and
- the Architect's activation decision.

The package format must not be designed or represented in MVP schema until
self-upgrade is promoted.

### 2.5 Clone qualification

The incumbent should:

1. close work admission and prove global quiescence;
2. take and hash a custom-format `pg_dump` of live PostgreSQL;
3. create an isolated, exactly named qualification database;
4. restore the dump;
5. start the candidate in qualification mode against only the clone and a
   cloned runtime manifest;
6. apply candidate migrations to the clone;
7. verify schema identity, constraints/indexes, audit/material-state
   consistency, CAS references, ticket readiness, campaign cost derivation,
   Forum search, and read-only status;
8. run restart and idempotency probes;
9. prove the candidate cannot touch the live database or product refs; and
10. seal qualification evidence before destroying the clone.

Promotion must settle the PostgreSQL administration contract. The likely
design is a dedicated non-superuser owner role with `CREATEDB`, while the
kernel restricts itself to catalog-verified, recorded qualification database
names. V3 must never install, start, stop, discover, or broadly delete a
PostgreSQL server or database fleet.

### 2.6 Live activation and rollback rehearsal

After clone qualification, the intended activation is:

1. retain the live dump, predecessor binaries/source/dependency material,
   active manifest, and append-only CAS;
2. stop the incumbent serving socket while retaining process custody;
3. apply the already-qualified transaction-safe migration to live PostgreSQL;
4. atomically switch the active-generation manifest;
5. start the candidate;
6. require lock acquisition, schema/audit checks, CAS sampling, and a read-only
   health response;
7. before work admission, stop the candidate, restore and health-check the old
   generation, then repeat the migration and candidate health check; and
8. open work admission only after that rollback rehearsal succeeds.

Failure before admission automatically restores the predecessor. After the new
generation accepts any mutating or paid work, snapshot rollback is forbidden;
recovery must roll forward so accepted work is never silently discarded.

The boot shim that selects a manifest should contain mechanism only, no policy
or qualification judgment. It is not an immutable warden and may itself be
replaced by a future authorized generation.

### 2.7 Expected new durable state and operator surface

Likely additions, only when promoted:

- `kernel_generations`;
- `generation_qualifications`;
- generation-package and migration artifact relations;
- activation/rollback Architect decisions;
- `factoryctl generation status`;
- `factoryctl generation qualify <package>`; and
- `factoryctl generation activate <qualified-generation>`.

Required tests include failure injection before and after dump, restore,
migration, manifest switch, candidate start, health, rollback, second
activation, and first post-admission command. They must prove clone isolation,
pre-admission restoration, post-admission roll-forward, and queryable lineage.

## 3. Other deferred candidates

### 3.1 Additional product-work contracts

The MVP and current product direction remain behavior-defect-only. Do not add a
`TicketKind` abstraction in anticipation of these possibilities.

If later selected, each work contract needs its own evidence rather than
reusing the defect reproducer fiction:

- a feature needs an independently sponsored public behavior contract and a
  failing acceptance test that does not assume the implementation;
- performance work needs a stable benchmark environment, repeated baseline,
  declared variance treatment, and minimum improvement threshold;
- dependency updates need a concrete compatibility/security objective and
  product behavior evidence;
- documentation-only changes need a user-facing correctness oracle; and
- refactor/cleanup work needs evidence that it removes a measured delivery or
  maintenance constraint without changing behavior.

None is scheduled for V1 merely by appearing here.

### 3.2 Bounded director delegation

MVP directors execute their own assignments. A later director may delegate to
a bounded subordinate worker only after evidence shows one-session office work
is the throughput constraint. A design must specify authority inheritance,
subordinate budgets, maximum fan-out, evidence custody, cancellation, and how
the director remains accountable for one terminal office result. It must not
introduce arbitrary organization graphs or worker reproduction.

### 3.3 Forum digests and notifications

Explicit indexed browsing/search is the MVP. Digests or notifications may be
added only after session evidence shows actors repeatedly miss relevant prior
Forum material. Any design must avoid per-user copied inbox rows, unread-write
amplification, ranking, engagement scoring, or live steering. A read-time
bounded digest derived from existing indexes is preferred.

### 3.4 Search improvements

Typo tolerance, fuzzy matching, and better code-token search are deferred until
real Forum queries demonstrate misses. PostgreSQL-native extensions or query
changes should be evaluated before adding another search service. Ranking by
reputation, votes, popularity, or institutional status is not part of this
candidate.

### 3.5 Concurrent paid work and multiple campaigns

MVP deliberately runs one paid Pi session and one campaign at a time. Any
concurrency, frontier scheduler, long-lived alternate world line, or
merge/reconciliation policy requires a new aggregate-cost reservation
protocol, repository and ticket fencing, delivery serialization, deterministic
scheduling, cancellation semantics, and tests for final-response cost
overshoot. It is not a WIP-limit configuration change.

### 3.6 Remote workers or multiple hosts

Remote execution requires authenticated transport, artifact transfer,
credential handling, leases/fencing, liveness, clock assumptions, and recovery
from partitions. HTTP is not presumed; the transport must be selected from the
actual deployment need. No remote-worker placeholder belongs in MVP.

### 3.7 Stronger actor isolation

MVP uses cooperative same-user host processes. Containers, VMs, seccomp,
network mediation, credential brokers, filesystem isolation, and adversarial
tenant claims are deferred architecture. Promotion requires a stated attacker
model and must preserve the current cooperative host/tool contract rather than
adding controls without a threat they address.

### 3.8 A second product application

The MVP proves the black-box boundary with XSH only. A second product may use
the closed application bundle after the first implementation demonstrates that
the contract is genuinely product-neutral. Promotion must not introduce a
runtime plugin loader or weaken Rust admission to accommodate product-specific
callbacks. If the second product needs a new authoritative concept, add one
explicit protocol/domain contract and test both applications against it.

### 3.9 Factory operational gaps

These are concrete candidates carried forward from the MVP implementation.
Each needs a focused contract, regression evidence, and an explicit V1
selection before implementation.

#### Engineering recovery

An Engineering worktree can currently be lost when the actor fails before
`candidate_submit`, even though the kernel can independently capture its tree,
binary patch, changed paths, and validation. After a successful regression
checkpoint, terminal reconciliation should preserve a changed worktree as
controller-owned recovery evidence and offer one explicit, bounded continuation
or validation path. Candidate completion and risk records remain kernel-sealed;
the gap is recovery before candidate submission.

#### Terminal-cost recovery

A host protocol failure after paid work can leave cost `unknown` and fail a
campaign even when provider usage and product changes are otherwise usable. The
host/kernel boundary needs a crash-safe, independently verifiable terminal
usage handoff that remains fail-closed when no measurement exists.

#### Scheduler throughput correctness

Rejection and infrastructure failure must not cause repeated paid Product
discovery for the same unmet demand. Scheduler transitions need a focused
real-driver test covering proposal, sponsorship, Engineering failure,
rework/recovery, and the one-delivery stop.

#### Retention and garbage collection

Worktrees and staging directories are transient and controller-removed, but
CAS objects have no lifecycle collector. Design an operator-invoked,
reference-safe CAS and stale-staging collector before long-running operation;
it must never remove evidence reachable from PostgreSQL or live runtime state.

#### Application authoring ergonomics

Template BLAKE3 pins and predecessor-bundle lineage are correct but manually
copied today. The compiler should derive and verify them from one declared
source of truth so a harmless prompt edit does not require hand-editing opaque
digests.

#### Factory self-improvement lane

Add a generic, non-product `factory-engineer` assignment path for this
repository's kernel, protocol, host, daemon, migrations, and operational
tooling, plus a separately bound maintenance path for the pinned
`/Users/josh/d/pi-agent-core-rs` checkout. Each target needs its own repository
binding, application policy/templates, reproducible validation profile, budget
accounting, Architect gates, and local delivery target without authority over
`../xsh`. Core changes must not run as an XSH assignment or mutate the core
checkout while an XSH campaign is active; after a delivered core change, the
operator must stop the daemon, rebuild the qualified host, and requalify the
fresh core source identity before paid work. Both lanes must use the exact
generic `CommitProvenance` trailer set used by XSH Engineering, including the
final commit-visible `Factory-Cost` trailer. They may address scheduler
throughput, operator-socket reliability, worktree cleanup, terminal-cost
recovery, and core-runtime defects as durable Factory changes while remaining
separate from XSH Product → Engineering → Quality work.

The existing `factory.tickets` relation is not a factory-engineering queue: it
is scoped to an admitted application revision, its proposal operation is
`product.submit_ticket`, and its downstream roles are the XSH Product →
Engineering → Quality chain. Do not route a core defect through that path or
rename the XSH Engineering office to make it appear generic. The lane must add
a distinct `FactoryTicketProposalV1` contract and durable queue with explicit
repository binding, base commit/tree, mission, acceptance criteria, required
reads, validation profile, sealed evidence, and bounded budget. It must expose
lane-qualified operator `factory ticket list/show` navigation and a separate
`factory-engineer` assignment target; a factory ticket must be impossible to
claim as an XSH ticket attempt. The first observability ticket should measure
each host tool execution by tool name, success/failure, total duration, and
maximum duration without persisting arguments or transcript text in PostgreSQL.

### 3.10 Published agent-core source

The current direct dependency on `/Users/josh/d/pi-agent-core-rs` is a
deliberate local bootstrap. A later source publication mechanism may replace
that absolute path, but it must retain an immutable, reproducibly qualified
source identity, clean-source refusal, lockfile binding, and the same host
boundary. Publication cannot introduce a floating revision, copied source,
compatibility runtime, or new Factory authority.

## 4. Explicitly rejected, not deferred

These ideas are not V1 backlog. Reconsidering one requires changing the product
direction, not merely completing a postponed task:

- importing or translating Factory V1/V2 state or code;
- a universal causal/epistemic graph or generic research ontology;
- universal logical worlds, multi-channel deltas, VM snapshots, or `smolworld`;
- scientific episodes, treatment arms, counterfactual organizations, actor
  genomes, role reproduction, selection, reinforcement learning, or scalar
  institutional fitness;
- arbitrary organization graphs, automated office occupancy, or dynamic office
  delegation;
- automatic ticket creation to satisfy buffer occupancy;
- per-department dollar budgets;
- a rolling agent handbook separate from XSH's canonical docs and the Forum;
- agent social graphs, markets, or social ranking; Forum votes, karma,
  reputation, consensus, private messages, or engagement ranking;
- semantic retrieval, embeddings, or a general information router;
- HTTP merely as a local control transport;
- a web dashboard or TUI before the CLI/status evidence proves inadequate;
- generic workflow, plugin, policy-expression, JSON Schema, EAV, JSONB metadata,
  full event-sourcing, projection, or internal message-bus frameworks;
- storing agent events, traces, searches, reads, tool calls, or transcript text in
  PostgreSQL;
- session resume for paid assignments;
- direct edits or commits in `../xsh`, worktree manipulation outside kernel
  custody, remote Git pushes, pull-request automation, deployment, or release
  actions;
- Tokio, async-std, an ORM, a Git library, or cryptographic randomness without
  a new requirement that the current stack cannot meet; and
- automatic snapshot rollback after a successor has accepted work.

## 5. First V1 planning gate

After MVP acceptance, inspect the campaign evidence and identify the single
largest measured constraint. Select at most one deferred candidate for the
first V1 implementation plan. Do not bundle self-upgrade, concurrency,
delegation, broader ticket types, and isolation into one release.
